### 1.2 关键差距

#### A. 协议层差距

| 差距项 | 当前实现 | 协议要求 |
|--------|----------|----------|
| 消息类型命名 | 下划线 `attendance_record` | 点分 `attendance.report` |
| 消息信封 | 不完整，缺 `inReplyTo`/`ack` | 完整信封含 10+ 字段 |
| 认证流程 | 无 `deviceId`/`deviceKey` 认证 | 首包必须 `auth`，否则 2001 |
| 二进制帧接收 | 未实现 | 4 字节 BE 长度前缀 + payload |
| 照片上传 | 未实现 | `awaitPhoto` + `attendance.photo.header` + 原始 JPEG |
| 设备状态上报 | 未实现 | `device.status.report` |
| 数据同步 | 无 | `sync.request` → `person.sync` × N → `face.sync.begin` → `face.sync.item.header` + 4+L → `face.sync.end` → `sync.ack` |
| 远程指令 | 未实现 | `device.command` → `device.command.ack` |

#### B. 数据库层差距

| 差距项 | 当前实现 | 规范要求 |
|--------|----------|----------|
| Person 表结构 | 嵌入式 face_feature BLOB，无 department/position | 独立的 `person` 表 (employee_id, name, department, position)，特征分离到 `face_feature` 表 |
| 人脸特征存储 | 混在 Person 表 `face_feature` 列 | 独立 `face_feature` 表 (employee_id PK, feature_blob, feature_size, sync_generation) |
| 离线队列 | 无出箱机制 | `attendance_outbox` 表 (pending/sending/failed/dead 状态机) |
| 同步代次 | 无 | `sync_meta` 表 (current_generation, staging_generation) |
| 本机信息 | 无 | `device_local` 表 |
| Schema 迁移 | 无 | `schema_version` 表 + 迁移脚本 |
| 照片存储 | 无 | `attendance_outbox.photo_blob` |

#### C. 架构层差距

| 差距项 | 当前实现 | 规范要求 |
|--------|----------|----------|
| 连接状态机 | 无显式状态 | Disconnected → Connected → Authenticated → (Syncing) |
| 模块分层 | 扁平结构 | 分层：Transport → Protocol → Business |
| 同步管理 | 无 SyncManager | 独立的 SyncManager 管理全量同步流程 |
| 指令处理 | 无 CommandHandler | 解释执行 reboot / resync 命令 |
| 离线重试 | 无 | outbox 出队 + 退避重试 + 死信标记 |

## 二、改造目标

### 2.1 总体目标

## 三、改造阶段规划

### 阶段一：协议层与传输层改造（基础）

**目标**：建立与服务端的标准通信通道，实现认证→心跳→断线重连的完整生命周期。

**改造内容**：

#### 3.1.1 重构 `ServerProtocol` → 统一协议层

- **文件**：`NetworkClient/serverprotocol.h` / `.cpp`
- **改动**：
  - 消息类型全部改为点分命名：`attendance.report`、`sync.request`、`person.sync`、`device.command` 等
  - 定义完整信封结构体 `Envelope`（含 `type`, `role`, `from`, `to`, `msgId`, `inReplyTo`, `ts`, `ack`, `code`, `msg`, `data`）
  - 实现 `buildEnvelope()` 统一构造方法
  - 废弃旧的 `Protocol` 命名空间（下划线命名），清理调用方
  - 消息类型常量与 `ProtocolTypes.hpp` 对齐

#### 3.1.2 改造 `Messagereader` → 支持二进制帧

- **文件**：`NetworkClient/messagereader.h` / `.cpp`
- **改动**：
  - 添加状态机：`LineMode` / `BinaryMode`
  - `LineMode`：现有行为，解析 JSON 行
  - `BinaryMode`：当解析到 `face.sync.item.header` 时自动切换，读取 `4 字节 BE 长度 → L 字节 payload`
  - 新增信号 `binaryFrameReceived(header, QByteArray payload)`
  - 接收缓冲区上限提升至 1 MiB + 4 KiB

#### 3.1.3 改造 `Messagewriter` → 支持二进制发送

- **文件**：`NetworkClient/messagewriter.h` / `.cpp`
- **改动**：
  - 添加 `sendBinaryFrame(const QByteArray &payload)` 方法
  - 照片发送**不**加 4 字节前缀（协议要求：设备→服务端照片为原始字节）
  - 添加 `sendRawJson(const QJsonObject &msg)` 内部方法

#### 3.1.4 改造 `Connectionmanager` → 连接状态机

- **文件**：`NetworkClient/connectionmanager.h` / `.cpp`
- **改动**：
  - 显式状态枚举：`Disconnected` / `Connecting` / `Connected` / `Authenticated`
  - 状态变更信号 `connectionStateChanged(ConnectionState old, ConnectionState new)`
  - 保留指数退避重连（1s × 2^n，最大 30s，最多 5 次）
  - 断连后自动重置状态为 `Disconnected`

#### 3.1.5 改造 `Heartbeatmanager` → 动态间隔

- **文件**：`NetworkClient/heartbeatmanager.h` / `.cpp`
- **改动**：
  - 心跳间隔从固定 3s 改为读取 `auth_response.data.heartbeatSec`（默认 30s）
  - 超时阈值 = heartbeatSec × graceMultiplier（默认 30 × 3 = 90s）
  - 收到任意消息重置超时计时器（不仅限于 heartbeat_response）

#### 3.1.6 重构 `Networkclient` → 认证流程与 sessionToken

- **文件**：`NetworkClient/networkclient.h` / `.cpp`
- **改动**：
  - 首包必须发送 `auth`（deviceId + deviceKey）
  - 处理 `auth_response`：提取 `heartbeatSec`，启动心跳
  - 认证失败 (code 2002/2003) 时的处理策略
  - `from` 字段统一使用 `deviceId`
  - `deviceId` 从 `device_local` 表或配置读取
  - 连接成功后按需发送 `device.status.report`

**阶段一验收标准**：
- [ ] 设备能成功 auth 并收到 `auth_response` (code=0)
- [ ] 心跳按服务端下发间隔正常收发
- [ ] 断线后自动重连并重新 auth
- [ ] JSON 行分帧正常工作
- [ ] 二进制帧接收（4+L）正常解析

### 阶段三：业务功能实现

**目标**：实现协议要求的全部设备端功能。

#### 3.3.1 考勤上报改造

- **改动文件**：`NetworkClient/networkclient.cpp`（`uploadAttendance` 方法）
- **新增功能**：
  - 先写入 `attendance_outbox`（`state=pending`），再异步发送
  - 发送时改 `state=sending`
  - 收到 `attendance.report.response` (code=0) 后删除 outbox 记录
  - 收到错误码时更新 `retry_count` 和 `last_error`，按规则设 `failed` 或 `dead`
  - 4011 (员工不存在) → `dead`
  - 6002 (数据库错误) → `failed`，指数退避重试
  - 网络断开 → `pending`，连接恢复后重试
  - 支持 `awaitPhoto` 流程：report → photo.header → JPEG raw bytes → response
  - 重试保持 `client_msg_id` 不变（幂等）

#### 3.3.2 实现同步管理器 `SyncManager`

- **新建文件**：`Sync/SyncManager.h` / `.cpp`
- **功能**：
  - 发送 `sync.request`
  - 接收 `person.sync`（多条合并 `persons` 数组）
  - 写入 staging 代次
  - 接收 `face.sync.begin`
  - 逐条接收 `face.sync.item.header` + 二进制特征，写入 staging 代次
  - 接收 `face.sync.end`
  - 校验：`feature_size` 与 blob 长度一致，外键完整性
  - 单事务代次切换：
    1. 删除 `sync_generation != staging_generation` 的旧数据
    2. 更新 `current_generation = staging_generation`
    3. 更新 `person_count` / `face_count`
  - 发送 `sync.ack` (status="ok") 或失败 ack
  - 同步期间拒绝重复 `sync.request`（并发互斥）
  - 失败不切换代次，保留旧数据继续服务
- **信号**：`syncStarted()`, `syncCompleted()`, `syncFailed(QString)`, `personSyncProgress(int)`, `faceSyncProgress(int)`

#### 3.3.3 实现指令处理器 `CommandHandler`

- **新建文件**：`Command/CommandHandler.h` / `.cpp`
- **功能**：
  - 接收 `device.command` 消息
  - 解析 `data.command` 字段
  - 支持指令：
    | command | 行为 |
    |---------|------|
    | `reboot` | 安全重启应用 |
    | `resync` | 触发 `sync.request` |
    | `set_time` | NTP 校时（可选） |
  - 发送 `device.command.ack`，`inReplyTo` = 服务端转发 `msgId`
  - 10 秒内必须回复（否则管理端超时 5002）

#### 3.3.4 实现设备状态上报

- **改动文件**：`NetworkClient/networkclient.cpp`
- **功能**：
  - 认证成功后发送 `device.status.report`（含 deviceName、ipAddress）
  - IP 变更时再次上报
  - 正确处理 `device.status.report.response`

#### 3.3.5 封装考勤上报器 `AttendanceReporter`

- **新建文件**：`Attendance/AttendanceReporter.h` / `.cpp`
- **功能**：
  - 封装 outbox 读取 → 发送 → 响应处理 → 清理 的完整流程
  - 支持批次上报（队列中多条）
  - 照片处理：从 outbox 读取 `photo_blob`，按 awaitPhoto 流程发送
  - 上报结果通过信号通知 UI

**阶段三验收标准**：
- [ ] 考勤上报（无照片）端到端成功，管理端可见
- [ ] 考勤上报（带照片）端到端成功，服务端 `photo` 列非空
- [ ] 离线打卡 → 恢复网络 → 自动上报 → 队列清空
- [ ] 全量同步完成，`person_count` / `face_count` 正确
- [ ] 同步后离职人员不在本地库
- [ ] `reboot` 命令能重启设备
- [ ] `resync` 命令触发同步
- [ ] `device.command.ack` 在 10s 内返回

```
  ├─ 3.1 考勤上报改造（outbox + 重试 + 照片）

       │
       ▼

  ├─ 4.2 配置扩展

```

阶段之间有严格依赖：阶段二依赖阶段一的协议层完成；阶段三依赖阶段二的数据库就绪；阶段四依赖前三阶段的功能模块就绪。

## 六、潜在风险与注意事项

### 6.1 技术风险

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| ArcFace SDK 与下发的特征维度不匹配 | 识别失败 | 以 `featureSize` 为准，不做硬编码；同步时校验维度 |
| 二进制帧 4+L 解析与 JSON 行交织 | 解析错乱 | 严格状态机，禁止在 BinaryMode 写入非心跳 JSON |
| 全量同步数据量过大 | 设备存储空间/内存不足 | 分页合并写入事务；VACUUM 维护；监控 DB 大小 |
| 线程安全（face 线程读 / sync 线程写） | 数据竞争 | WAL 模式；识别只读当前代次；代次切换短暂阻塞识别 |

### 6.2 协议注意事项

- **设备→服务端照片无 4 字节前缀**，服务端→设备特征有 4 字节前缀（不对称，易出错）
- **`device.command.ack` 的 `inReplyTo` 必须是服务端转发 msgId**，不是管理端原始 msgId
- **`sync.ack` 服务端不回复**，仅记日志与失败计数
- **挂起态**：`awaitPhoto=true` 时只能发 `heartbeat` 和 `attendance.photo.header`，否则取消挂起
- **service端同时接受 camelCase 和 snake_case**，但设备发送建议统一 camelCase

### 6.3 数据库注意事项

- 设备禁止直连 MySQL；仅使用本地 SQLite
- `deviceKey`、sessionToken 不入库
- 同步中途**不**清空当前生效代次数据（等 face.sync.end 后再切换）
- 外键约束：无 person 不能插入 face_feature
