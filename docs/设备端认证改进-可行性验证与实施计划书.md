## 3. 风险点识别

| 风险 | 严重程度 | 说明 | 应对措施 |
|------|----------|------|----------|
| **密钥明文存储** | 🔴 高 | `key_hash` 列实际存储明文密钥，不是真正的哈希 | 建议在实施时改用 SHA-256 或 bcrypt 哈希，服务端比较哈希值而非明文 |
| **数据库兼容性** | 🟡 中 | `status` 列是 `VARCHAR(20)`，现有数据含 `'pending_auth'` | 部署前执行数据迁移脚本，将所有 `pending_auth` 状态改为 `offline` |
| **协议兼容性** | 🟡 中 | 旧设备端可能仍发送旧格式认证请求 | 确保服务端新旧协议短暂共存，或统一升级所有设备 |
| **回滚复杂度** | 🟡 中 | 删除 `pending_device_auth_` 后回滚需要恢复较多代码 | 使用 git 管理，保留原代码在独立分支 |
| **管理端 deviceKey 输入安全性** | 🟢 低 | UI 上 deviceKey 输入框应使用密码模式 | 将 QML TextField 的 `echoMode` 设为 `TextInput.Password` |

## 4. 详细实施计划

### 4.1 服务端修改 (D:\attendanceServer)

#### 步骤 1: 新增 `device.create` 命令处理

**文件**: `protocol/GatewaySessionHandler.cpp`

在命令分发逻辑中新增 `device.create` 处理分支：

```
权限校验 (Admin + device.create 权限)
  → 校验 deviceId / deviceKey 非空
  → 对 deviceKey 做哈希 (SHA-256)
  → INSERT INTO Device (device_id, device_name, key_hash, status)
  → 返回 device.create.response
```

**需要同步修改**:
- `protocol/ProtocolTypes.hpp`: 新增 `kTypeDeviceCreate` 常量
- `db/DeviceRepository.cpp`: 新增 `createDevice` 方法（或复用 `insertDevice` + key_hash 参数）
- `util/`: 新增或复用哈希工具函数

#### 步骤 2: 简化 `handleDeviceAuth` 函数

- 移除 `pending_auth` 判断分支（设备不存在 或 status=pending_auth+key_hash为空 → 直接返回 "device not registered"）
- 保留：查询设备 → 验证密钥 → 注册会话 → 构建响应 → 更新 online → 推送事件
- TokenManager::authenticateDevice 返回的 JWT 令牌保持不变

#### 步骤 3: 清理待审核相关代码

删除以下内容：
- `GatewaySessionHandler.hpp`: `PendingDeviceAuth` 结构体、`pending_device_auth_` 成员变量
- `GatewaySessionHandler.cpp`: `kTypeDeviceAuthApprove` 处理分支（约 130 行）
- `GatewaySessionHandler.cpp`: `kTypeDevicePendingAuthPush` 推送调用
- `GatewaySessionHandler.cpp`: `erase_connection` 中清理 `pending_device_auth_` 的代码
- `db/DeviceRepository.cpp`: `upsertDevicePendingAuth` 方法
- `protocol/ProtocolTypes.hpp`: `kTypeDevicePendingAuthPush`、`kTypeDeviceAuthApprove`、`kTypeDeviceAuthApproveResponse` 常量（可选保留以兼容）

#### 步骤 4: 改进密钥存储安全性

在 `DeviceRepository` 中新增密钥哈希方法，将 `key_hash` 列改为存储真正的 SHA-256 哈希值：

```cpp
// 新增工具函数
std::string hashDeviceKey(const std::string& deviceKey) {
    // SHA-256 哈希
}
```

同步修改 `TokenManager::verifyDeviceKey`，改为比较哈希值而非明文。

#### 步骤 5: 数据库迁移

```sql
-- 清理待审核状态的设备
UPDATE Device SET status = 'offline' WHERE status = 'pending_auth';

-- 可选：将 status 改为 ENUM 类型
ALTER TABLE Device MODIFY COLUMN status ENUM('offline', 'online') DEFAULT 'offline';
```

|----------|----------|

## 7. 与方案文档的差异说明

原方案文档整体方向正确，以下为实际验证后发现的需调整之处：

| 条目 | 原方案描述 | 实际发现 | 调整建议 |
|------|-----------|----------|----------|
| `device.create` 处理 | 在 GatewaySessionHandler 中新增 | **确认需要新增**——当前服务端未处理此命令 | 按方案执行 |
| `key_hash` 安全性 | 未明确提及哈希方式 | 当前为**明文存储**，存在安全风险 | 增加 SHA-256 哈希步骤 |
| 管理端 Device 模型 | 未提及需修改管理端 | **deviceKey 字段不存在**，createDevice 不发送密钥 | 增加管理端修改任务 |
| Device 表 status 类型 | 建议用 ENUM | 当前为 `VARCHAR(20)` | 可选的迁移 SQL |
| 设备端改动 | 仅提及配置文件 | 设备端还有**待审核重试逻辑**需清理 | 增加设备端代码清理任务 |
| `device.create` 在管理端 | 未提及 | **已存在**，只是缺少 deviceKey 参数 | 仅需修改参数，无需从零开发 |
