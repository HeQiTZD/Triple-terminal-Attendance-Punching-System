# 项目深度学习和理解文档 — attendanceServer

## 一、项目概述

这是一个 **C++17 考勤服务器**，基于 TCP 协议与考勤设备/管理客户端通信，使用 MySQL 持久化数据，集成虹软（ArcSoft）人脸识别引擎。构建系统为 CMake，依赖 Boost.Asio 做异步 I/O。

**核心业务流程**：考勤设备通过 TCP 连接服务器 → 人脸比对/打卡 → 考勤记录入库 → 管理端通过 TCP 连接查询/管理。

## 三、模块详解

### 1. `config/` — 配置模块

#### 文件职责

| 文件 | 职责 |
|---|---|
| `ServerConfig.hpp/cpp` | 定义 `ServerConfig` 结构体（DB、TCP、TLS、ArcFace、Gateway、RBAC 等全部配置项），含 `PendingSuperAdmin` |
| `ConfigFile.hpp/cpp` | 从 `attendance.json` 加载/解析配置，解析命令行参数 |
| `ConsoleConfigUi.hpp/cpp` | 交互式终端配置向导（首次运行时引导用户设置） |

#### 设计思路

配置系统采用 **三层覆盖策略**：内置默认值 → 环境变量 `ATTENDANCE_*` → 命令行参数（后者覆盖前者）。

`ServerConfig` 是一个纯数据聚合结构体，将所有子系统的配置集中在一个地方：

```cpp
// config/ServerConfig.hpp:28
struct ServerConfig {
  db::DbConfig db;                    // 数据库连接参数
  bool enable_tcp = false;            // 是否启用 TCP 网关
  std::string tcp_bind = "0.0.0.0";  // 监听地址
  unsigned short tcp_port = 8080;     // 监听端口
  std::size_t tcp_worker_threads = 0; // 0 = auto
  std::size_t db_pool_threads = 0;
  protocol::GatewayConfig gateway;    // 网关协议行为参数
  ArcFaceConfig arcface;              // 人脸识别 SDK 配置
  std::optional<PendingSuperAdmin> pending_super_admin; // 运行时临时字段
};
```

`PendingSuperAdmin` 是一个设计亮点：明文密码仅在内存中短暂持有，不序列化到 JSON，用完即清零。

#### 开发思路

- `loadServerConfig()` 是配置加载的主入口，内部调用链：`resolveConfigPath()` → `loadFromJson()` → `apply_env()` → `parse_*()` → `applyConfigDefaults()`
- 环境变量通过 `getenv_copy()` 读取，使用 `std::from_chars` 做高性能数值解析（避免 `std::stoi` 的异常开销）
- `ConsoleConfigUi` 提供菜单式交互（1-数据库、2-TCP网关、3-线程池、4-协议行为、5-ArcFace、7-保存启动、8-注册超管），首次运行时自动进入

#### 数据流

```
attendance.json ──┐
环境变量 ATTENDANCE_* ──┤──→ loadServerConfig() ──→ ServerConfig 结构体
命令行参数 ───────────┘         │
                               ├──→ makeTcpServerConfig() ──→ net::TcpServer::Config
                               └──→ logConfigSummary() ──→ 控制台输出
```

#### 设计思路

**Repository 模式**：每个业务实体对应一个 Repository 类，所有方法都是静态方法，直接接收 `mysqlx::Session&` 作为参数。这样做的好处是：
- Repository 不持有连接状态，便于在不同上下文中复用
- 与 `ConnectionPool`/`DbExecutor` 解耦，Repository 只关心 SQL 操作

**连接池设计**（`ConnectionPool.hpp`）：

```cpp
// db/ConnectionPool.hpp:18
class ConnectionPool {
  // 固定大小连接池。acquire() 阻塞等待可用连接；release() 做健康检查，
  // 失败则自动重建连接再归还。
  std::shared_ptr<mysqlx::Session> acquire() {
    std::unique_lock<std::mutex> lk(mu_);
    cv_.wait(lk, [this] { return !pool_.empty(); });  // 阻塞等待
    auto sess = std::move(pool_.front());
    pool_.pop();
    return sess;
  }

  void release(std::shared_ptr<mysqlx::Session> sess) {
    // SELECT 1 健康检查，失败则重建连接
    try { sess->sql("SELECT 1").execute(); } catch (...) {
      sess = std::make_shared<mysqlx::Session>(DbClient::connection_url(cfg_));
    }
    std::lock_guard<std::mutex> lk(mu_);
    pool_.push(std::move(sess));
    cv_.notify_one();
  }
};
```

关键特性：
- 构造时预创建所有连接（`pool_size` 个）
- `acquire()` 使用 `condition_variable` 阻塞等待，池空时自动挂起调用线程
- `release()` 做 `SELECT 1` 健康检查，连接断开则自动重建，对调用方透明
- 析构时优雅关闭所有连接

#### 开发思路

- `Schema::ensure_tables()` 在启动时自动建表（IF NOT EXISTS），`ensure_rbac_seed_data()` 插入默认角色和权限
- `main.cpp` 中的 `createSuperAdminIfPending()` 使用事务确保 Person + UserAccount + RoleAssignment 的原子性
- 所有 Repository 的输入/输出都是独立的结构体（如 `AttendanceRecordCreateInput`），与 MySQL SDK 解耦

#### 数据流

```
ConnectionPool::acquire()
       │
       ▼
  mysqlx::Session（从池中借出）
       │
       ▼
  Repository::insertXxx(session, input)  ──→  MySQL X DevAPI  ──→  MySQL 数据库
       │
       ▼
  ConnectionPool::release(session)  ──→  SELECT 1 健康检查  ──→  归还池中
```

### 3. `net/` — 网络层

#### 文件职责

| 文件 | 职责 |
|---|---|
| `TcpServer` | TCP 监听器，accept 连接，创建 Session，管理 worker 线程池 |
| `SessionBase<T>` | 会话基类模板（CRTP），管理读写循环、帧缓冲、strand 串行化 |
| `Session` / `SessionV2` | 明文 TCP 会话实现（`SessionBase<tcp::socket>`） |
| `TlsSession` / `TlsSessionV2` | TLS 加密会话实现（`SessionBase<ssl::stream<tcp::socket>>`） |
| `Framing` | 帧分隔逻辑（行分隔 `\n`、二进制帧 4字节BE长度前缀）和大小限制 |
| `TlsConfig` | TLS 证书/密钥配置 |
| `ISession` | 会话公共接口（write_line/write_binary/begin_expect_binary/request_close） |
| `ISessionHandler` | 会话事件回调接口（on_line/on_binary/on_error/on_close） |

#### 设计思路

**核心架构：Reactor + Strand 串行化**

```
TcpServer (io_context + N worker threads)
    │
    ├── accept → 创建 Session → session->start()
    │
    └── 每个 Session 绑定一个 strand（保证该连接的所有操作串行执行）
```

`SessionBase<Stream>` 使用 **CRTP 模板** 统一 TCP 和 TLS 会话的公共逻辑：

```cpp
// net/SessionBase.hpp:17
template <typename Stream>
class SessionBase : public ISession {
  // 子类只需实现 do_read() 和 do_write_front()
  virtual void do_read() = 0;
  virtual void do_write_front() = 0;

  // 公共的帧处理逻辑
  void process_received_bytes(const char* data, std::size_t len);
  void process_line_frames();       // 文本行模式
  void consume_recv_into_binary();  // 二进制帧模式
};
```

**双模式接收**（`RxMode`）：
- `Lines` 模式：按 `\n` 分隔文本行，每行回调 `handler_.on_line()`
- `Binary` 模式：按 4 字节大端长度前缀接收二进制数据，完成后回调 `handler_.on_binary()`

通过 `begin_expect_binary(byte_count)` 在 Lines 和 Binary 模式之间切换，支持"先发文本声明，再发二进制数据"的考勤照片上传流程。

**线程安全**：每个 Session 通过 `boost::asio::strand` 保证该连接上的所有读写操作串行执行，避免锁竞争。`write_line()` 和 `write_binary()` 都通过 `boost::asio::post(strand_, ...)` 投递到 strand。

**写队列**：`write_queue_`（`std::deque<std::vector<char>>`）实现写缓冲，`enqueue_write()` 在 idle 时触发 `do_write_front()`，写完成后从队列取下一段。

#### 开发思路

- `TcpServer::start()` 内部流程：`bind` → `listen` → `do_accept()` 投递异步 accept → 创建 `work_guard` 防止 `io_context` 退出 → 启动 N 个 worker 线程
- `Session::start()` 被 `TcpServer::do_accept()` 在 accept 成功后调用，开始第一个异步读
- `ISessionHandler` 是网络层与协议层的唯一接口，网络层完全不知道 JSON/业务语义
- 错误处理：`fail()` 关闭 socket → `handler_.on_error()` → `handler_.on_close()`，保证每个 Session 最多触发一次 close

#### 数据流

```
设备/客户端 TCP 连接
       │
       ▼
  TcpServer::do_accept()  ──→  new Session(socket, handler)  ──→  session->start()
       │
       ▼
  Session::do_read()  ──→  async_read_some  ──→  on_read_some()
       │
       ▼
  SessionBase::process_received_bytes()
       │
       ├── RxMode::Lines  ──→  process_line_frames()  ──→  handler_.on_line(session, line)
       │
       └── RxMode::Binary  ──→  consume_recv_into_binary()  ──→  handler_.on_binary(session, payload)

  handler_.on_line() / on_binary()  ──→  进入 protocol 层
```

**消息处理器注册表**（`MessageHandlerRegistry`）：

```cpp

  using MessageHandler = std::function<void(
      Session& session, const Envelope& env, Context& ctx, const std::string& route_to)>;

```

使用 `std::function` 存储处理器，通过 `register_handler(type, handler)` 注册，`find(type)` 查找。模板化设计使得注册表与具体 Session/Envelope/Context 类型解耦。

#### 开发思路

**GatewaySessionHandler 的消息处理流程**：

`on_line()` 是所有文本消息的入口，内部流程：

1. JSON 解析 → `try_parse_envelope()` 提取信封
2. **认证分支**：
   - `type == "device.auth"` → `handleDeviceAuth()` → 验证设备密钥 → 生成 JWT 令牌对 → 注册到 `DeviceRegistry`
   - `type == "admin.auth"` → `handleAdminAuth()` → 验证用户名密码 → 加载 RBAC 角色权限 → 生成 JWT → 注册到 `AdminRegistry`
   - `type == "token.refresh"` → `handleTokenRefresh()` → 刷新令牌
3. **已认证消息**：`verifyTokenInEnvelope()` 验证 JWT → 从 `connections_` map 获取 `ConnContext` → 查找 `handler_registry_` → 调用对应 Handler
4. **心跳管理**：每个连接认证后启动 `steady_timer`，超时未收到心跳则断开

`on_binary()` 处理二进制帧（如考勤照片），根据 `ConnContext::pending_binary` 判断类型。

**RBAC 权限热加载**：`reload_permissions()` 在角色变更后重新从数据库加载权限，通知在线管理员刷新。

#### 数据流

```
Session::on_line(line)  ──→  GatewaySessionHandler::on_line()
       │
       ▼
  nlohmann::json::parse(line)
       │
       ▼
  try_parse_envelope(json)  ──→  ParsedEnvelope
       │
       ├── type == "device.auth"  ──→  handleDeviceAuth()
       │       │
       │       ├── TokenManager::authenticate_device(device_id, key)
       │       │       └── verify_device_key() ──→ DB 查询
       │       │       └── generate_token_pair() ──→ JWT 签名
       │       │
       │       ├── DeviceRegistry::register_or_replace()
       │       └── session.write_line(成功响应 + tokens)
       │
       ├── type == "admin.auth"  ──→  handleAdminAuth()
       │       │
       │       ├── TokenManager::authenticate_admin(username, password)
       │       │       ├── verify_admin_password() ──→ DB 查询 + 密码哈希比对

       └── 其他已认证类型  ──→  verifyTokenInEnvelope()
               │
               ▼
          handler_registry_.find(type)  ──→  调用具体 Handler
```

#### 设计思路

**DbExecutor — 异步数据库执行器**

```cpp
// service/DbExecutor.hpp:21
class DbExecutor : public IDbExecutor {
  // 池线程从连接池获取连接，归还时自动健康检查 + 断连重建
  void dispatch(Work work, Done done) override;
private:
  std::shared_ptr<db::ConnectionPool> conn_pool_;
  std::unique_ptr<boost::asio::thread_pool> pool_;
};
```

`dispatch(Work, Done)` 是核心接口：
- `Work` = `std::function<void(mysqlx::Session&)>` — 在池线程中执行的数据库操作
- `Done` = `std::function<void()>` — 操作完成后的回调（在调用方 strand 中执行）

工作流程：`dispatch()` → 投递到 `thread_pool` → 池线程调用 `conn_pool_->acquire()` 获取连接 → 执行 Work → `conn_pool_->release()` 归还连接 → 调用 Done 回调。

**DeviceRegistry / AdminRegistry — 在线连接注册表**

两者都使用 `weak_ptr<ISession>` 存储会话引用，避免阻止 Session 销毁：

```cpp
// service/DeviceRegistry.hpp:16
class DeviceRegistry : public IDeviceRegistry {
  // deviceId → weak_ptr<ISession>，支持单播/广播
  void with_session(const std::string& device_id,
                    std::function<void(net::ISession&)> fn);
  template <typename Fn>
  void for_each_device(Fn&& fn);  // 广播：遍历所有在线设备
};
```

`for_each_device()` 先在锁内做 snapshot（提升 `weak_ptr` 为 `shared_ptr`），再在锁外遍历调用，避免长时间持锁。

**MessageRouter — 管理端指令转发**

```cpp
// service/MessageRouter.hpp:25
class MessageRouter {
  // 管理端 device.command → 设备 → ack 回管理端；默认超时 10s
  void forward_device_command(admin_sess, env, operator_id);
  // 服务端主动下发指令（如配置部署）
  ForwardResult forward_server_device_command(device_id, data, msg_id_seed, on_ack, on_timeout);
};
```

核心机制：
1. 管理端发 `device.command` → `MessageRouter` 生成新 `forward_id` → 转发给目标设备
2. 设备回复 `device.command.ack`（`in_reply_to = forward_id`）→ `handle_device_command_ack()` → 回调 `on_ack` → 转发给管理端
3. 超时（10s）→ `on_timeout` 回调 → 通知管理端超时
4. `Pending` 结构体持有 `steady_timer` + 管理端会话引用 + ACK/超时回调

**TokenManager — JWT 令牌管理**

```cpp
// service/TokenManager.hpp:40
class TokenManager {
  DeviceAuthResult authenticate_device(device_id, device_key);  // 设备认证
  AdminAuthResult authenticate_admin(username, password);       // 管理员认证
  std::optional<TokenPair> refresh_tokens(refresh_token);       // 刷新令牌
  std::optional<TokenPayload> verify_access_token(token);       // 验证令牌
  void revoke_token(jti);                                        // 撤销令牌
};
```

认证流程：验证凭据 → 生成 access_token（短生命周期）+ refresh_token（长生命周期）→ 返回 `TokenPair`。支持令牌撤销（强制下线）。

**ArcFaceEngine — 单例 + 线程安全**

```cpp

class ArcFaceEngine {
public:
  static ArcFaceEngine& instance();  // Meyers' Singleton
  bool initialize(app_id, sdk_key);  // 在线激活 + 初始化引擎
  FaceExtractResult extract_feature_from_image_file(image_path);
private:

  std::atomic<bool> m_initialized;
```

人脸特征提取流程：
1. `stbi_load()` 加载图片 → RGB 转 BGR（SDK 要求）
2. 宽度 4 字节对齐（SDK 要求）
3. `ASFDetectFacesEx()` 检测人脸 → 校验人脸数量（必须为 1）→ 校验人脸尺寸（≥80px）
4. `ASFFaceFeatureExtractEx()` 提取特征向量
5. 返回 `FaceExtractResult`（含特征数据 + 人脸位置信息）

使用 `std::mutex` 保护所有 SDK 调用（虹软 SDK 非线程安全），`std::atomic<bool>` 做初始化状态的快速检查。

## 六、关键设计模式

| 模式 | 实现 | 作用 |
|---|---|---|
| **Repository** | `PersonRepository`, `DeviceRepository` 等 | 每个实体一个 Repository，静态方法接收 `mysqlx::Session&` |
| **Handler 注册表** | `MessageHandlerRegistryT<Session, Envelope, Context>` | `unordered_map<string, function>` 实现消息类型 → 处理器的动态映射 |
| **连接池** | `ConnectionPool` (acquire/release + 健康检查 + 自动重建) | 复用 MySQL 连接，避免频繁创建销毁 |
| **异步执行器** | `DbExecutor` (thread_pool + ConnectionPool) | 将 DB 操作 dispatch 到独立线程池，不阻塞 I/O 线程 |
| **CRTP** | `SessionBase<Stream>` | 模板化 TCP/TLS 会话公共逻辑，子类只实现 `do_read()`/`do_write_front()` |
| **接口抽象** | `IDbExecutor`, `IDeviceRegistry`, `ISession`, `ISessionHandler` | 依赖倒置，便于 Mock 测试 |
| **单例** | `ArcFaceEngine::instance()` (Meyers' Singleton) | 全局唯一的人脸识别引擎实例 |
| **RBAC** | `RoleRepository` + `ConnContext::permissions` | 基于角色的访问控制，权限缓存在连接上下文中 |
| **Weak_ptr 注册表** | `DeviceRegistry`, `AdminRegistry` | 使用 `weak_ptr<ISession>` 避免阻止 Session 销毁 |
| **Strand 串行化** | `SessionBase::strand_` | 保证每个连接的操作串行执行，避免锁竞争 |
